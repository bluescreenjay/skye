# Tasks: Workspace Agents

**Input**: Design documents from `/specs/010-workspace-agents/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/http.md, contracts/model.md, contracts/shared-agent-types.md, quickstart.md

**Tests**: Included, as the plan specifies: Vitest on PGlite with an injected fake agent model and a fake page reader (no network), table tests for the address rules, HTML fixtures, extension unit tests for the pure client helpers, and one opt-in live check. They never touch Tiger and never call a real provider or the internet by default. Drop the test tasks (T017, T018, T025, T030, T031, T036, T039, T042, T046, T051, T055, T056) if you want none; nothing else depends on them except that the helper file (T015) is used by them.

**Organization**: Grouped by user story from spec.md (US1 to US7). US1 to US6 are P1 and US7 (history) is P2. The run pipeline is built up in layers: US1 runs an agent from tab excerpts only, US2 adds the checklist writes, US3 adds real page reading, US4 to US5 harden it, US6 puts it on the Home card, and US7 adds history. Each story's Independent Test passes with only the stories before it.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an unfinished task)
- **[Story]**: US1 to US7, only inside story phases
- Paths are from the repository root.

**Rules for the implementer**
- Every model request goes through `apps/web/src/llm/` (provider choice, daily budget, concurrency limiter). Never call a vendor from agent code. One AI request per run, made only after a press.
- Every SQL statement is parameterized and filters by `user_id` **and** the workspace id. Cast bare parameters in a `SELECT` or `INSERT ... SELECT` (`$1::uuid`): Postgres cannot infer their type there.
- Never log tab titles, addresses, excerpts, page text, prompts, model output, results, plan item text, or chat messages. Log ids and counts only, and never put any of them in an error body either. Stored run errors are the fixed sentences in `contracts/http.md`, never text from the AI service.
- **The page reader is safety-critical.** Never weaken an address rule to make a test pass. No test may open a connection to the internet or to a private address (the one real-socket test uses a loopback listener and asserts it receives **no** connection). The reader must send no cookies or credentials.
- Check real exit codes: run typecheck and tests without piping them through `tail` (a pipe hides the failing exit status).
- Vitest hides `console.log` output of passing tests; for live checks pass `--disable-console-intercept`.
- `apps/web/AGENTS.md` warns this Next.js differs from older versions. The new routes are ordinary JSON handlers (`200`, `202`) like the existing ones; do **not** use `after()` (research 1). Copy the shape of `apps/web/app/api/workspaces/[id]/chat/route.ts` (`runtime = "nodejs"`, `OPTIONS`, CORS via `src/json.ts`).
- Extension: `.ts` files outside `home/` and `sidebar/` are scanned by `tests/observe-only.test.ts` (no `chrome.tabs.*`, `document.createElement`, `innerHTML =`, and so on). The shared code in `apps/extension/src/ui/` must not touch those; the host passes in how to open a tab. React StrictMode runs effects twice: guard async effects with a per-run `cancelled` flag, not a shared ref (the chat panel had exactly this bug).
- `next build` overwrites `.next`, which a running `next dev` uses. If a dev server is running, build from a scratch copy of the app with `next build --webpack` (see the saved note on verifying a build with a dev server running) instead of building in place.
- Never run anything against the Tiger database except where a task says it needs the user's approval (T060, T061). Do not commit. Do not edit `spec.md`, `plan.md`, or `data-model.md`; if reality contradicts them, stop and say so. (The plan already records the one correction made at task time: the client lives in `apps/extension/src/ui/`.)

## Implementation Strategy

### MVP First (User Story 1 only)

1. Phase 1 Setup, then Phase 2 Foundational (stop at its checkpoint, T016).
2. Phase 3 (US1). **Stop and validate**: the four text-like agents produce saved, validated, workspace-only results from tab excerpts, and the press returns at once.
3. That is a working agents server, though not yet checklist-aware, page-reading, hardened, or visible on Home.

### Incremental Delivery

1. Foundation → US1 (real saved results).
2. US2 adds the checklist and its ticks, and connects the feature to chat.
3. US3 adds real page reading. This is the feature's largest risk and the reason agents beat chat; do not skip the mutation check (T038).
4. US4 makes it strictly bounded (the trust story) and US5 makes failures safe. Together US1 to US5 are the server side.
5. US6 puts it on the Home card, which is what people will judge. Start its client and tests early in parallel if there are two people.
6. US7 adds history. Polish, then the manual database and live checks.

### Notes

- Do not apply the migration to Tiger, or run the live quickstart, until T060 and T061 are approved.
- Do not commit; tasks are checked off as they complete.
- If reality contradicts `plan.md`, `spec.md`, or `data-model.md` (for example a provider rejects one of the answer schemas, or a site's compression trips the size cap unexpectedly), stop and say so rather than editing them.
- The lesson from 004 and 008: run against the real provider early. A model can behave differently from the fake (a schema change once made Gemini drop a whole group), so T059 is not optional in spirit even though it is opt-in in code. A live run of the reader against real public pages (quickstart V2, V5, and V6) is the only check that the hand-written HTML extraction and the redirect and sign-in rules hold up on the real web.
